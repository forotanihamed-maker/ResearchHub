# ResearchHub — وضعیت پروژه و مسیر پیش‌رو

> **این سند یک فایل زنده‌ی وضعیت (Living Status Doc) است.** هدفش این است که هر دستیار هوش مصنوعی یا فردی که کار را ادامه می‌دهد، بدون نیاز به مرور کل تاریخچه‌ی گفت‌وگو، دقیقاً بداند چه کاری شده، الان در چه مرحله‌ای هستیم، و چه کاری باقی مانده. **بعد از هر جلسه‌ی کاری جدید، این فایل باید به‌روزرسانی شود** (بخش‌های ۲، ۳، ۴ را ویرایش کنید؛ بخش ۱ ثابت می‌ماند مگر ماهیت محصول تغییر کند).

---

## ۱. یادآوری یک‌خطی پروژه

ResearchHub سامانه‌ای است که استاد پروژه‌ی پژوهشی تعریف می‌کند، دانشجو درخواست عضویت می‌دهد، استاد تأیید/رد می‌کند، و تیم شکل‌گرفته در یک فضای مشترک کار می‌کند؛ یک پنل ادمین دپارتمانی هم روی این فرآیند نظارت دارد. هدف فعلی، پذیرش در مرکز رشد واحدهای فناور دانشگاه علم و صنعت ایران (IUST) و اجرای یک Pilot واقعی در یک دانشکده، به‌عنوان بنیان‌گذار تکی.

## ۲. کارهایی که تا الان انجام شده

*(از مرحله‌ی تحقیق درباره‌ی مرکز رشد به بعد — تاریخچه‌ی رفع باگ‌های اولیه‌ی محصول، جدا از این سند نگه‌داری می‌شود.)*

### ۲.۱ تحقیق و شناخت مسیر نهادی

- بررسی کامل فرآیند «مرکز رشد واحدهای فناور دانشگاه علم و صنعت ایران» (`incub.iust.ac.ir`): دوره‌ی پیش‌رشد → تبدیل به شرکت فناور → دوره‌ی رشد.
- ⚠️ **یافته‌ی مهم:** خود سایت رسمی IUST در دو صفحه‌ی مختلف، دو عدد متفاوت برای مدت دوره‌ی پیش‌رشد اعلام کرده (۳ ماه در یک صفحه، ۶ ماه در صفحه‌ی دیگر). این عدد هنوز با خود مرکز تأیید نشده — **باید حتماً موقع تماس/ثبت‌نام پرسیده شود.**
- بررسی فرآیند «تاییدیه فنی نرم‌افزار» (سازمان فناوری اطلاعات ایران، `ito.gov.ir`): مشخص شد این تاییدیه بخشی از فرآیند ثبت مالکیت نرم‌افزار است (نه جدا از آن)، پرتال دقیق آن `iranspo.ir` (تاییدیه فنی) و سپس `samandehi.ir` (ثبت نهایی نزد وزارت ارشاد) است. یک اصلاح مهم نسبت به فرض اولیه: **دیگر نیازی به مراجعه‌ی حضوری به دفترخانه برای تعهدنامه نیست** — فقط تأیید خود متقاضی کافی است.
- نتیجه‌گیری: تاییدیه فنی منطقاً *بعد از* ثبت شرکت معنا پیدا می‌کند؛ در مرحله‌ی فعلی اقدامی لازم نیست.

### ۲.۳ تصمیم درباره‌ی بسته‌ی ارسالی به مرکز رشد

فقط ۳ فایل باید ضمیمه شود: `ResearchHub_BusinessPlan`، `ARCHITECTURE.md`، `SECURITY.md`. بقیه‌ی اسناد برای مخزن کد/تیم داخلی می‌مانند، نه برای ارسال.

### ۲.۴ تحلیل چک‌لیست نهایی کاربر (`ResearchHub_Pre_Growth_Center_Checklist.md`)

این چک‌لیست دریافت و دو مورد فنی‌اش با کد واقعی پروژه راستی‌آزمایی شد:

- **تأیید شد** — هیچ Unique Constraint سطح دیتابیس برای جلوگیری از Application تکراری وجود ندارد؛ فقط یک چک سطح‌کد وجود دارد که در شرایط race condition قابل‌دور زدن است.
- **تأیید شد** — API جزئیات پروژه (`GET /api/projects/[id]`) هیچ فیلتری بر اساس status پروژه برای دانشجو ندارد؛ یعنی پروژه‌ی بسته هم از طریق ID مستقیم قابل مشاهده است.

نتیجه: این چک‌لیست معتبر و به‌روز است؛ به‌عنوان مبنای بخش «کارهای باقی‌مانده» (بخش ۴) استفاده شده.

### ۲.۵ تحلیل و اولویت‌بندی فایل‌های بازخورد کاربر (`Problems.doc`, `Feature_List.doc`)

۱۸ مورد (۷ مشکل + ۱۱ فیچر پیشنهادی) بررسی و به سه دسته تقسیم شد:
- **قبل از مرکز رشد:** تغییر رمز عبور بعد از ثبت‌نام (در حال حاضر هیچ راهی برای آن وجود ندارد)، فارسی‌سازی رابط کاربری اصلی (لاگین، داشبورد)
- **بعد از پذیرش، قبل/حین Pilot:** یک زیرساخت مشترک «آپلود فایل» که سه نیاز را هم‌زمان پوشش می‌دهد (تکمیل پروژه، اشتراک فایل در چت، آرشیو مستندات پروژه)
- **بعد از داده‌ی واقعی Pilot، نه حدسی:** بهبود چت، جست‌وجوی مهارت، رزومه، commit-style activity log
- **رد شد / scope creep واقعی:** مدیریت پایان‌نامه، ارتباط با صنعت، مدیریت کارآموزی، مدیریت آزمایشگاه، AI — این‌ها هرکدام عملاً یک محصول جداگانه‌اند؛ ساختشان پیش از اعتبارسنجی محصول اصلی توصیه نمی‌شود.

### ۲.۶ نقشه‌ی راه ۶ ماهه

یک نقشه‌ی راه ماه‌به‌ماه نوشته شد (خلاصه‌اش در بخش ۵ همین سند). فرض‌های اصلی آن (زمان بررسی شورای رشد، پیدا شدن استاد حامی) هنوز اعتبارسنجی نشده‌اند.

## ۴. کارهای باقی‌مانده

### ۴.۱ ضروری، قبل از باز کردن سامانه به یک کاربر واقعی (دانشجو/استاد)

از ترکیب چک‌لیست کاربر + یافته‌های این گفتگو:

- [ ] افزودن Unique Constraint دیتابیسی برای جلوگیری از Application تکراری (نه فقط چک سطح کد)
- [ ] اصلاح Visibility پروژه‌های بسته در `GET /api/projects/[id]` برای نقش دانشجو
- [ ] بررسی نهایی Authorization/دسترسی مستقیم با ID در تمام endpointها
- [ ] بررسی افشای Email اعضای پروژه (Privacy)
- [ ] اجرای تست کامل Workflow: استاد → پروژه → دانشجو → درخواست → تأیید → تیم
- [ ] اجرای تست دسترسی غیرمجاز (manual یا خودکار)
- [ ] اجرای `typecheck` و `build` بدون خطا
- [ ] بررسی نبود Secret در Repository (`.gitignore` واقعاً اضافه و اعمال شده؟ — در بررسی قبلی این گفتگو هنوز اضافه نشده بود)
- [ ] حذف/تغییر رمز حساب‌های Demo پیش از Pilot واقعی
- [ ] حذف داده‌های نمایشی Seed از محیط Pilot
- [ ] افزودن صفحه‌ی Privacy Policy / Terms of Service (از بررسی قبلی این گفتگو، هنوز اضافه نشده)
- [ ] افزودن قابلیت «تغییر رمز عبور بعد از ثبت‌نام» (در حال حاضر هیچ endpointی برای این کار وجود ندارد)
- [ ] فارسی‌سازی رابط کاربری اصلی (لاگین، داشبورد، پنل ادمین) برای دموی جلوی شورای رشد

### ۴.۲ اسناد/مواد باقی‌مانده برای جلسه‌ی مرکز رشد

- [ ] نسخه‌ی نهایی Pitch Deck کوتاه (اسلایدی، جدا از سند Word کامل)
- [ ] لینک یا نسخه‌ی Demo پایدار (دیپلوی‌شده، قابل نمایش زنده)
- [ ] یک Architecture Diagram تصویری ساده (نه فقط متن — یک نمودار بصری)
- [ ] یک Product Demo Flow یک‌صفحه‌ای (سناریوی نمایش کوتاه و مشخص)
- [ ] اصلاح هرگونه آمار نمایشی روی Landing Page که مبتنی بر داده‌ی واقعی نیست
- [ ] آماده‌سازی توضیح ۲ تا ۳ دقیقه‌ای شفاهی محصول

### ۴.۳ اقدام نهادی

- [ ] ارسال رسمی درخواست پذیرش در `incub.iust.ac.ir`
- [ ] پرسیدن صریح مدت دقیق دوره‌ی پیش‌رشد (۳ یا ۶ ماه؟ — تناقض سایت رسمی هنوز حل نشده)
- [ ] یافتن یک استاد/دانشکده‌ی حامی برای Pilot، **موازی با روند بررسی، نه بعد از آن**

### ۴.۴ عمداً به تعویق افتاده (طبق چک‌لیست کاربر و این گفتگو — نباید مانع مراجعه به مرکز رشد شود)

Pilot با کاربران زیاد، اولین قرارداد پولی، Product-Market Fit، معماری چندمستأجری، اپلیکیشن موبایل، چت کاملاً Real-time، اشتراک‌گذاری فایل، Email Notification، Password Recovery (فراموشی رمز — متفاوت از «تغییر رمز» که در ۴.۱ ضروری علامت خورده)، تیم کامل، مدل مالی چندساله‌ی دقیق، AI، مدیریت پایان‌نامه/کارآموزی/آزمایشگاه/ارتباط با صنعت.

## ۵. خلاصه‌ی نقشه‌ی راه ۶ ماهه

| بازه | تمرکز اصلی |
|---|---|
| ماه ۱ | رفع موارد بخش ۴.۱ (امنیت/آماده‌سازی) + ارسال درخواست به مرکز رشد + شروع جست‌وجوی استاد حامی |
| ماه ۲ | (در انتظار بررسی شورای رشد) قطعی‌کردن استاد/دانشکده + شروع ساخت زیرساخت آپلود فایل |
| ماه ۳-۴ | اجرای Pilot واقعی یک ترم + جمع‌آوری متریک هفتگی (بخش ۶ چک‌لیست کاربر) |
| ماه ۵ | تحلیل نتایج Pilot + تأیید مدت دقیق پیش‌رشد با IUST + آماده‌سازی ثبت شرکت |
| ماه ۶ | تبدیل Pilot موفق به قرارداد پرداختی + ساخت پرونده‌ی مرجع برای دانشکده/دانشگاه بعدی |

⚠️ این جدول بر پایه‌ی فرض‌هایی است که هنوز اعتبارسنجی نشده‌اند (سرعت پاسخ شورای رشد، سرعت یافتن استاد حامی). با هر اتفاق واقعی، این بخش باید بازنویسی شود.

## ۶. یادداشت برای دستیار/مدل بعدی

اگر این گفتگو را با یک مدل یا دستیار دیگر ادامه می‌دهی:

1. **این فایل را قبل از هر پیشنهاد جدید کامل بخوان** — تکرار کاری که قبلاً انجام یا رد شده (مثلاً ساخت مدیریت پایان‌نامه) اتلاف وقت است.
2. **هیچ ادعایی درباره‌ی وضعیت کد را بدون بررسی مستقیم فایل‌های واقعی پروژه نپذیر.** در طول این پروژه چند بار مستندات با کد واقعی مغایرت داشت (نمونه: ادعای نادرست تست خودکار در `SECURITY.md`، ایمیل‌های seed ناهماهنگ با صفحه‌ی لاگین). همیشه کد را چک کن، نه فقط این سند را.
3. **بعد از هرکاری که انجام می‌دهی، بخش‌های ۲، ۳، و ۴ همین فایل را به‌روزرسانی کن** — آیتم‌های چک‌لیست را تیک بزن، بخش «در چه مرحله‌ای هستیم» را با وضعیت واقعی جدید جایگزین کن، و اگر فرضی (مثل مدت پیش‌رشد) اعتبارسنجی شد، عدد قطعی را جایگزین علامت ⚠️ کن.
4. **اولویت فعلی تیم، اعتبارسنجی است، نه تکمیل محصول.** قبل از پیشنهاد هر فیچر جدید، این سؤال را از کاربر یا از خودت بپرس: «آیا نبودن این قابلیت مانع اجرای Pilot یا یادگیری از کاربر واقعی می‌شود؟» اگر جواب نه است، فعلاً در اولویت نیست (این اصل مستقیماً از چک‌لیست خود کاربر گرفته شده و باید حفظ شود).
